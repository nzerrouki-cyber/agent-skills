# Proof-of-Concept: Core Vertex AI Agentic Pipeline

This document describes the end-to-end architecture for integrating custom Google Gems into an automated, production-grade agentic workflow hosted on Google Cloud Platform (GCP) within Costco’s Innovation Intake Agentic Workflow. 

## 0\. Mandatory Initial Step: Pipeline Bootstrapping & Skill Pre-Seeding

Before any user traffic or agentic workflows can execute, the system requires a mandatory deployment bootstrapping step to seed core system skills and domain knowledge bases:

1. **Production GCS Skill Pre-Seeding**:  
   1. System Core Skills (`SKILL_GEM_CREATOR`, `SKILL_INTAKE`, `SKILL_VALIDATION`) and pre-seeded skills (`SKILL_CSA_REVIEW`, `SKILL_ARCH_RISK_REVIEW`, `SKILL_TECHNICAL_REVIEW`, `SKILL_CDS_DATA_EVALUATOR`), that serve as knowledge for GemCreator Agent, are uploaded directly to `gs://enterprise-skillbank/production/<skill_id>.md`.  
2. **Skill Registry Index Population**:  
   1. A deployment script (`scripts/seed_skills.py`) registers each seeded skill into Firestore (`skill_registry` collection) recording `skill_id`, `generation_id`, `gcs_uri`, `target_datastore_id`, `category`, `output_schema`, and `status: "ACTIVE"`.  
3. **Vertex AI Search Data Store Ingestion**:  
   1. Structural reference files grounding `GemCreatorAgent` (`CSA Review Gem.md`, `Arch Risk Review Gem.md`, `Technical Review Gem.md`, `CDS Data Intake Advisor.md`) are ingested into the `system-core-ds` Data Store.

---

1\. Skill Bank & Skill Validation Pipeline (Two-Stages)

The skill bank that stores all of the skills will be hosted onto **GCS Bucket w/ Object Versioning**. This GCS Bucket i.e `gs://enterprise-skillbank/<stage>/<skill_id>`, will be comprised of two stages:

1. **Draft Stage:** Stores new skills that were generated by the Gem Creator or added to the repository by the user.   
   1. Stored in `gs://enterprise-skillbank/drafts/<skill_id>.md` via GCS client library (google-cloud-storage).  
2. **Promotion & Validation:** Skills that were successfully validated by the Skill Validation Agent. This agent will audit the skill via:  
   1. **Structural Audit:** Verifies that the skill adheres to the standard prompt framework.   
   2. **Security Gate Audit:** Verifies that there are no security issues.  
   3. **Cryptographic Sign Check:** Verifies that the file’s hash matches the skill’s index.  
   4. Stored in `gs://enterprise-skillbank/production/<skill_id>.md.`  
3. **Retrieval:** Skills that were successfully validated can be retrieved at runtime via CoreService, from the Discovery Agent through this directory. This way, the Discovery Agent can route the Skill.md and intake.md at run-time to be enqueued by the **Cloud Task Queue** at run-time.

---

2\. Core Agentic Workflow: The Orchestrator Pattern

The architecture operates on a **Multi-Agent Orchestrator (Supervisor) Pattern**.

* **The Orchestrator Agent (Supervisor):** Serves as the primary front-door gateway for all user interactions. It maintains conversational state, parses the initial prompt, and utilizes LLM function-calling/tool-calling to determine intent.  
* **Service Abstraction:** The Orchestrator does not execute business logic. Instead, it dynamically routes requests by invoking available backend services (tools).  
* **Agent Delegation:** Upon a tool call, the Orchestrator delegates context to a specialized sub-agent. Once the sub-agent completes its task, it returns the output or state back to the Orchestrator.

---

## 3\. Microservice Deployment, Ingress & Security Architecture

All sub-agents (`IntakeAgent`, `GemCreatorAgent`, `ValidationAgent`, and `DiscoveryAgent`) run as isolated, stateless backend microservices hosted on **Google Cloud Run**.

* **Cloud Run Native HTTPS Ingress:** Communication between the Orchestrator Agent and backend sub-agents uses native Cloud Run HTTPS endpoints. TLS termination is managed natively by Cloud Run infrastructure.  
* **Internal Ingress Control:** Sub-agent Cloud Run services configure their ingress setting strictly to **`Internal`** (or `Internal + Cloud Load Balancing`), blocking public internet access and restricting calls exclusively to internal Google Cloud network routes.  
* **Service-to-Service IAM Authentication:** Every tool call invocation from the Orchestrator to a backend sub-agent is authenticated using Google Cloud IAM OpenID Connect (OIDC) Bearer tokens (`Authorization: Bearer <ID_TOKEN>`).  
* **Stateless JSON Invocation:** Tool calls pass structured JSON parameters (such as `gcs_uri` pointers) over HTTPS POST requests, keeping container executions stateless, horizontally scalable, and cost-optimized (scaling down to zero when idle).

---

## 4\. Service Modules & Specialized Agents

The Orchestrator interacts with modular backend Cloud Run services, each wrapping a specialized agent:

* **IntakeService (`IntakeAgent`):** Manages conversational extraction of innovation ideas, returning turn-by-turn prompts until the final structured payload is written to GCS.  
* **DiscoveryService (`DiscoveryAgent`):** Retrieves skills via Vertex AI Search Data Stores, caches prompts in local working memory, and executes skills directly (bypassing legacy worker containers).  
* **GemCreatorService (`GemCreatorAgent`):** Handles prompt creation and tuning. Supports low-latency GCS URI retrieval for existing skills as well as direct Markdown uploads for new drafts.  
* **ValidationService (`ValidationAgent`):** Executes automated test suites, anti-hijack audits, schema verifications, and handles promotion from GCS Staging to GCS Production.

## 5\. Deep Dive: Core Sub-Workflows

### A. Innovation Intake Process

1. **User Request & Extraction:** User prompts the application to submit a new innovation intake form. The Orchestrator routes the session to `IntakeService` and proxies conversational extraction turns.  
2. **Raw State Persistence (GCS):** Upon completion, `IntakeAgent` writes the raw JSON payload to `gs://skill-bank/intakes/raw/{intake_id}.json`, returns `STATUS: COMPLETE`, and unpins `IntakeAgent`.  
3. **Asynchronous Sanitization (Eventarc & Model Armor):** The GCS write fires an Eventarc trigger, invoking Model Armor via Cloud Run to sanitize the intake payload (scanning for PII and prompt injections) and persisting the clean payload to `gs://skill-bank/intakes/sanitized/{intake_id}.json`.  
4. **Decoupled User Selection:** The user later interacts with the Orchestrator Agent and explicitly references an intake idea to execute (e.g., *"Process my HR automation intake idea"*).  
5. **Sanitized Service Handoff:** The Orchestrator resolves the intake reference, locates its sanitized storage path (`gs://skill-bank/intakes/sanitized/{intake_id}.json`), and issues an HTTPS tool call to `DiscoveryService` passing the sanitized `gcs_uri` pointer.  
6. **Discovery, Caching & Direct Execution:** `DiscoveryAgent` fetches the sanitized payload directly from GCS, queries Vertex AI Search Data Stores to discover the appropriate skill, caches it in memory for low Time to Last Syllable (TLS), executes it directly, and returns results to the Orchestrator.

### B. Gem Creation & Modification Process

1. **User Request:** User requests to modify an existing skill or create a new Gem.  
2. **Orchestration Routing & Resolution:**  
   * **Existing Skill:** The Orchestrator resolves the skill ID to its production GCS path (`gs://skill-bank/production/skills/{skill_id}.md`) and passes the `baseline_gcs_uri` to `GemCreatorService` via HTTPS without loading the raw prompt into its own context window.  
   * **New Skill / Draft Upload:** The Orchestrator passes the raw text/Markdown payload directly via HTTPS.  
3. **Ingestion & Modification:** `GemCreatorAgent` fetches the prompt directly from GCS Production via Cloud SDKs, executes edits in working memory, writes candidate drafts to `gs://skill-bank/staging/`, and returns candidate and baseline GCS URIs to the Orchestrator.  
4. **Validation Routing:** The Orchestrator receives candidate URIs and issues an HTTPS tool call to `ValidationService`.

### C. Skill Validation Process

#### **1\. Initial Creation Validation Flow (New Gem)**

1. **Draft Staging:** `GemCreatorAgent` completes initial prompt synthesis and writes the draft prompt to `gs://skill-bank/staging/new_skill_candidate.md`, returning the GCS URI to the Orchestrator.  
2. **Orchestration & Validation Handoff:** The Orchestrator issues an HTTPS tool call to `ValidationService` (`ValidationAgent`) with the staging GCS URI.  
3. **Automated Evaluation Execution:**  
   * **Syntax & Formatting Gate:** Verifies Markdown structural cleanliness, required taxonomy sections, and token limits.  
   * **Prompt Defense Audit:** Scans for systemic vulnerabilities, anti-hijack mechanisms, and negative prohibitions.  
   * **Synthetic Schema & Execution Sandbox:** Generates synthetic test inputs and executes the candidate prompt in an isolated Vertex AI sandbox to verify output schema compliance (e.g., valid JSON/Pydantic).  
4. **Promotion or Feedback Loop:**  
   * **PASS:** `ValidationAgent` promotes the candidate file to `gs://skill-bank/production/skills/{skill_id}.md`, re-indexes the Vertex AI Search Data Store, and returns `Status: APPROVED` to the Orchestrator.  
   * **FAIL:** `ValidationAgent` logs structured error diagnostics and returns `Status: REJECTED` to the Orchestrator to trigger an automated remediation loop with `GemCreatorAgent`.

#### **2\. Refinement Validation Flow (Existing Gem Modification)**

1. **Delta Drafting & Handoff:** `GemCreatorAgent` fetches the active baseline from GCS Production, applies edits, writes candidate drafts to `gs://skill-bank/staging/{skill_id}_candidate.md`, and returns candidate and baseline GCS URIs. The Orchestrator passes both URIs to `ValidationService`.  
2. **Delta & Regression Evaluation Suite:**  
   * **Diff Audit:** Inspects prompt changes between baseline and candidate versions to verify core safety rules and output schemas remain intact.  
   * **Historical Regression Test:** Runs the candidate prompt against historical benchmark inputs to guarantee zero functional regressions.  
   * **Target Delta Test:** Evaluates edge cases specific to the requested refinement.  
3. **Deployment, Versioning & Cache Invalidation:**  
   * **PASS:**  
     1. Archives the active prompt to `gs://skill-bank/archive/{skill_id}_v{timestamp}.md`.  
     2. Promotes candidate draft to `gs://skill-bank/production/skills/{skill_id}.md`.  
     3. Invalidates active `DiscoveryAgent` semantic cache or short-term memory keys tied to `{skill_id}` so subsequent calls immediately load the updated prompt.  
     4. Re-indexes Vertex AI Search Data Stores and returns `Status: APPROVED` to the Orchestrator.  
   * **FAIL:** Active production prompt remains untouched. Diagnostic failure logs are sent to the Orchestrator for auto-remediation by `GemCreatorAgent`.

## 6\. DiscoveryAgent: RAG Context & Queue Handoff

When the Orchestrator requests an intake evaluation, it invokes the DiscoveryService tool, passing the sanitized GCS URI to the DiscoveryAgent.

* **Dynamic RAG Assembly:** The DiscoveryAgent assumes responsibility for the knowledge retrieval phase, querying the designated Vertex AI Search Data Store. It strictly enforces boundary caps of top\_k=3 or top\_k=5 to minimize latency and context window overhead.  
* **Context Packaging:** The agent packages the retrieved RAG context, the sanitized intake payload from GCS, and the active system prompt retrieved from the Cloud Memorystore Redis cache.  
* **Asynchronous Batching:** To protect Vertex AI quotas from bulk form submissions, the DiscoveryAgent enqueues this fully assembled payload into a Google Cloud Tasks queue (worker-dispatch-queue) configured with strict dispatch rates and concurrency limits. It then immediately returns a "Job Queued" status to the Orchestrator to keep the UI responsive.

---

## 7\. Asynchronous Execution via skill\_bank\_tool.py

The Cloud Tasks queue throttles traffic and systematically dispatches payloads to the execution adapter.

* **Schema Binding:** The tool adapter explicitly binds the required Pydantic output schema (e.g., SecurityAuditResult) to the request options.  
* **Constrained Inference:** It executes the model call against Gemini 2.5 Flash through the Apigee LLM Gateway, enforcing token-level constrained decoding (response\_mime\_type="application/json") to guarantee 100% schema-compliant output.  
* **Stateless Termination:** Because the legacy worker containers have been deprecated, this execution step runs entirely statelessly, parsing the response natively into a Python object via the google-genai.
