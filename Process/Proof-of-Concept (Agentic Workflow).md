# Proof-of-Concept: Enterprise Innovation Intake Pipeline via Vertex AI

This document describes the end-to-end architecture for integrating custom Google Gems into an automated, production-grade agentic workflow hosted on Google Cloud Platform (GCP) within Costco’s Innovation Intake Agentic Workflow. 

---

1\. Skill Bank & Skill Validation Pipeline (Two-Stages)

The skill bank that stores all of the skills will be hosted onto **GCS Bucket w/ Object Versioning**. This GCS Bucket i.e `gs://enterprise-skillbank/<stage>/<skill_id>`, will be comprised of two stages:

1. **Draft Stage:** Stores new skills that were generated by the Gem Creator or added to the repository by the user.   
   1. Stored in `gs://enterprise-skillbank/drafts/<skill_id>.md` via GCS client library (google-cloud-storage).  
2. **Promotion:** Skills that were successfully validated by the Skill Validation Agent. This agent will audit the skill via:  
   1. **Structural Audit:** Verifies that the skill adheres to the standard prompt framework.   
   2. **Security Gate Audit:** Verifies that there are no security issues.  
   3. **Cryptographic Sign Check:** Verifies that the file’s hash matches the skill’s index.  
   4. Stored in `gs://enterprise-skillbank/production/<skill_id>.md.`  
3. **Retrieval:** Skills that were successfully validated can be retrieved from the Discovery Agent through this directory. This way, the Discovery Agent can route the Skill.md and intake.md at run-time to be enqueued by the **Cloud Task Queue** at run-time.

---

## 2\. Intake Ingestion & Conversational Engine

Users submit an intake idea by interacting with an Agent i.e Intake Agent. This Intake Agent will have to be hosted on GKE using two distinct architecture zones, one for enabling the agent to communicate with the user with low latency and the other to store the chat session.

Synchronous Conversational Engine (Stateful Chat) 

1. **API Gateway & Ingress Layer: GKE Ingress Controller** with **WebSockets** or HTTP/2 Server-Sent Events (SSE), so then we can maintain persistent and low-latency connections between the Intake Agent and the user.  
2. **Live Session Chat Store:** Store the conversation history and current turn state, after answering each intake question, within **Google Cloud Firestore** or **Cloud Memorystore (Redis).**  
3. **Intake Agent Microservice (GKE):**   
   1. Intake Agent that receives the user’s incoming message alongside the session id  
   2. Fetches the conversation history and the current state from the **Live Session Chat Store**.  
   3. Has a gem system prompt for asking the user specific intake questions, validating the answers, and receiving any RAG inquiries from the user.

Handoff Gate & Asynchronous Pipeline Transition

1. **Verification:** After the user answers all of the necessary questions, the Intake Agent receives verification from the user and then updates the session status in the **Live Session Chat Store** as COMPLETED.  
2. **Payload Serialization:** Executes an **event trigger** or **Cloud Function / AppScript webhook** to read the COMPLETED document and converts it into a markdown file.  
   1. A unique submission id is assigned to that file.  
3. **GCS Ingestion:** The markdown file is sent to the GCS Bucket with its submission id.  
4. **Handoff:** GCS (storage.objects.f1.finalized) \-\> EventArc Trigger \-\> Model Armor \-\> Discovery Agent. 

---

3\. Discovery & Routing Pipeline

1. The Discovery Agent receives the markdown file of the intake through a **GKE Ingress**.  
   1. **GKE Ingress** ensures that the HTTP payload is being routed to the correct address.  
2. Inspects the metadata of the intake submission.  
3. Evaluates the category of the intake and matches it to a specific skill ID in the skill. The Discovery Agent can only retrieve this skill if it's a **promoted skill** within the skill bank.  
4. The Discovery Agent enqueues the promoted skill and intake.md via a throttled **Cloud Tasks queue**.   
   This will queue be configured with **Traffic Control & Rate Limiting:**  
   1. Configured with strict dispatch rates (`max_dispatches_per_second`) and concurrency limits (`max_concurrent_tasks`).  
   2. Smooths out traffic spikes from bulk form submissions, preventing `429 Resource Exhausted` quota errors on Vertex AI API calls.

---

4\. Worker Agent Execution

1. The worker agent pulls the tasks from the **Cloud Tasks queue**.  
2. Authenticates via Workload Identity and appropriate IAM permissions.  
3. Retrieves skill.md and ingests it into the system\_instruction parameter alongside the intake.md.  
4. Queries the knowledge files from the **Vertex AI Search Data Stores** at runtime through an on-demand RAG query, from the appropriate Data Store.  
   1. Each Data Store is mapped to a specific domain or category of the intake idea.  
   2. **Retrieval Guardrails:** Strict boundary caps (`top_k=3` or `top_k=5`) and chunk limits should be enforced during search retrieval to minimize execution latency and context overhead.  
   3. **Redis Caching:** Once the skill is downloaded, the worker will use an internal redis store by using a key : value store, where the key \= \<skill\_id\>:\<generation\_id\>.  
5. Enforce Pydantic response schemas (`response_schema=SecurityAuditResult`, `response_mime_type="application/json`) .  
6. Output is then streamed to a BigQuery DB using Storage Write API, saved to GCS for front-end rendering.
